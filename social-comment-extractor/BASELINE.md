## 🔍 pattern ที่พลาด (วิเคราะห์จากภาพรวม ไม่ได้ไล่ทีละข้อ)

> ตรงกับข้อ 5 ใน README ของชุด dataset ที่เขียนเตือนไว้แล้วว่า eval เป็นคอมเมนต์เดี่ยว ไม่มีโพสต้นเรื่อง
> **ตอนใช้งานจริงไม่มีปัญหานี้** เพราะระบบดึงคอมเมนต์จากโพสที่ระบุมาอยู่แล้ว
> · เทียบตัวเลข: มีชื่อ CP ในข้อความ 77.4% · ไม่มีชื่อ 76.5% → **ชื่อ CP ไม่ใช่ตัวแปร บริบทต่างหาก**
> · ความแม่นแยกตามหัวข้อต่างกันมาก: "อื่นๆ" 56% · "ต้นตอ/ฟอกขาว" 65% ↔ "แรงงาน" 100% · "สิ่งแวดล้อม" 87%

## 🧪 รอบ 3 — แก้ prompt 3 ข้อ (rubric v4)

ทุกข้อ**ย้อนกลับไปหา rubric ได้** ไม่ใช่แก้ให้ตรงข้อสอบทีละใบ:

1. **ไม่เอ่ยชื่อ CP แต่ชมสิ่งที่โพสนำเสนอ = Positive** — rubric ให้ข้อยกเว้นนี้กับ*การกล่าวหา*
   ("เจ้าสัว/บริษัทที่ปล่อยปลา") แต่ไม่เคยเขียนด้านกลับของมันไว้ · นี่คือการเติมให้สมมาตร
2. **ชี้ตัวคนทำ (ผู้นำเข้า/ต้นตอ/นายทุน) = Negative · พูดถึงมาตรการ-กฎหมายลอยๆ = Neutral**
   — เดิม prompt เขียนว่า "นายทุน เจ้าสัว = Negative" แบบไม่มีเงื่อนไข ซึ่ง**ขัดกับตาราง rubric เอง**
   ที่ระบุว่า "ด่าบริษัท/ทุนแบบทั่วไป ไม่เอ่ย CP = Neutral"
3. **ประชด = ใช้ถ้อยคำบวกแต่ความหมายด่าเท่านั้น** — ด่าตรงๆ/เยาะเย้ย/🤣 ไม่ใช่ประชด
   และ**ห้ามให้ธงประชดไปเปลี่ยนป้ายของ 2 แกน** (รอบ 1 พบว่า 26 ใน 42 ข้อที่ทายประชดเกิน
   ถูกลากให้แกน 1 กลายเป็น Negative ตามไปด้วย)

+ few-shot 4 ข้อใหม่จาก `train`+`real` (2 ข้อสอนกฎ 1 · 2 ข้อสอนกฎ 2)

### ทำไมกฎข้อ 2 ไม่ทำงาน — เจอสาเหตุแล้ว

ใน 14 ข้อที่ยังพลาด (ชุดออกแบบ) **6 ข้อมีการด่ารัฐปนอยู่ด้วย**
"ชาติหน้าก็ไม่ได้แก้เพราะ**รัฐกลัวนายทุน**" · "**เจ้าหน้าที่รัฐเอื้อนายทุน**" · "**กรมประมง**ปกปิดช่วยบริษัทอะไรอยู่"

→ กฎ **"ด่ารัฐ ≠ ด่า CP"** ที่เขียนไว้เด่นๆ **ดูดประโยคพวกนี้ไปเป็น Neutral ทั้งหมด**
ทั้งที่ประโยคเดียวกันนั้นชี้ว่า**มีนายทุนได้ประโยชน์อยู่ด้วย** ซึ่ง rubric ให้เป็น Negative

### และกฎข้อ 1 ยิงเกินไป 1 กลุ่ม (14 ข้อ)

"น่าจะเอาปลามาแปรรูปขาย" · "ส่งเข้าโรงงานสร้างรายได้สิ" · "ปลานี่ก็กินได้นะ อร่อย"
= **เสนอความเห็นว่าควรทำอะไร ไม่ใช่ชมผลงานของเจ้าของโพส** แต่ถูกตีเป็น Positive

## 🧪 รอบ 4 — prompt v5 แก้ 2 จุดนี้ตรงๆ

1. **ชี้ตัวคนทำ = Negative แม้จะด่ารัฐไปพร้อมกัน** ถ้าประโยคบอกว่ารัฐ *เอื้อ/อุ้ม/ไม่กล้าแตะ* นายทุน
   · กฎ "ด่ารัฐ ≠ ด่า CP" ใช้เฉพาะประโยคที่**ด่ารัฐล้วนๆ ไม่มีนายทุนอยู่ในนั้น**
2. **ชม = ชมสิ่งที่เจ้าของโพสทำหรือขายเท่านั้น** · ข้อเสนอแนะว่าควรทำอะไร → Neutral

+ few-shot 3 ข้อจาก `train`+`real`

> มาจาก**รายการที่ทายผิดใน eval โดยตรง** (id 77) ซึ่งเป็นข้อสอบรั่วเต็มๆ · ตัวตรวจจับได้ที่ความคล้าย 1.00

## 🔴 แต่ชุดสอบไล่บอกความจริงอีกอย่าง — **prompt เริ่มติดข้อสอบแล้ว**

| | แกน 1 Negative recall |

**ห่างกัน 12.5 จุด** = ส่วนต่างนี้คือ "ความเก่งเฉพาะข้อที่เคยเห็น" ไม่ใช่ความเก่งจริง

> 🎯 **ตัวเลขที่ควรเชื่อคือ 73.2% ไม่ใช่ 85.7%** — และตัวเลขรวม 79.5% ก็สูงเกินจริงเพราะครึ่งหนึ่งของมัน
> มาจากชุดที่ใช้ออกแบบ · **การแบ่งชุดสอบไล่ไว้ตั้งแต่รอบ 3 คือสิ่งเดียวที่ทำให้รู้เรื่องนี้**

## 🧪 รอบ 5 — เปลี่ยน **โมเดล** ไม่แตะ prompt

เหตุผลที่ไม่แก้ prompt ต่อ: แก้อีกก็จะยิ่งฟิตกับชุดออกแบบ แล้วช่องว่าง 12.5 จุดจะกว้างขึ้น
ส่วนการเปลี่ยนโมเดลเป็นตัวแปรที่**ไม่ได้เรียนรู้จากข้อสอบเลย** — ถ้าดีขึ้น แปลว่าดีขึ้นจริงทั้งสองฝั่ง

Worker v9 เปิดให้หน้าวัดผลเลือกโมเดลได้ (`claude-haiku-4-5` / `claude-sonnet-5` / `claude-opus-5`)
· 🚫 รับเฉพาะชื่อในรายการตายตัว — `/classify` ใครก็ยิงได้ ถ้ารับชื่ออะไรก็ได้จะโดนสั่งใช้ตัวแพงรัวๆ

**สิ่งที่ยังค้าง (ทำหลังผ่านเกณฑ์):** ประชดตกเหลือ 33.3% — แต่ทั้งชุดมีแค่ **12 ข้อ**
ผิดเพิ่มข้อเดียว = ตัวเลขเด้ง 8 จุด **น้อยเกินกว่าจะใช้ตัดสินใจอะไรได้** ต้อง label เพิ่มก่อน

## รอบ 5 — เปลี่ยนโมเดลเป็น `claude-sonnet-5` (ไม่แตะ prompt เลย)

**ตัวเลขรวมดูแย่ลงนิดเดียว แต่ความหมายกลับด้านกับที่เห็น**

| แกน 1 Negative recall | รอบ 4 (haiku) | รอบ 5 (sonnet) | |
|---|---|---|---|
| ชุดออกแบบ (id คี่) | 85.7% | 78.6% | **−7.1** |
| **ชุดสอบไล่ (id คู่)** | 73.2% | **78.0%** | **+4.9** ← ตัวที่สำคัญ |
| **ช่องว่างระหว่าง 2 ชุด** | **12.5 จุด** | **0.5 จุด** | เกือบหายสนิท |

### อ่านผลยังไง

`haiku` ทำคะแนนสูงในชุดออกแบบเพราะ **จำตัวอย่างใน prompt ไปตอบ** — พอเจอข้อที่ไม่เคยเห็น ตกเหลือ 73.2%
`sonnet` ทำได้ **เท่ากันทั้งสองฝั่ง (78.6 / 78.0)** = เข้าใจกฎจริง ไม่ได้จำตัวอย่าง

> 🎯 **ของจริง sonnet เก่งกว่า haiku ~5 จุด** (78.0 เทียบ 73.2 บนข้อที่ไม่เคยเห็น)
> ทั้งที่ตัวเลขบนหน้าจอบอกว่า haiku ดีกว่า · **ถ้าไม่มีชุดสอบไล่ เราจะเลือกผิดตัว**

### ผลพลอยได้

ช่องว่างที่หายไปเปลี่ยนความเสี่ยงของการแก้ prompt ด้วย — ตอน `haiku` การแก้ prompt จากชุดออกแบบ
ทำให้ฟิตกับชุดนั้นอย่างเดียว · ตอน `sonnet` สองชุดขยับไปด้วยกัน **pattern ที่เจอในชุดออกแบบน่าจะใช้ได้จริง**

## 🚫 รอบ 6 — opus · ผลนี้ใช้ไม่ได้ เป็นบั๊กของระบบวัดเอง

ตัวเลขที่ออกมา (Negative recall 10.8% · Neutral recall 97.5%) **ไม่ใช่ความสามารถของ opus**

หลักฐาน: **377 จาก 475 แถว (79%) ตอบ `Neutral / Neutral / 0` เหมือนกันเป๊ะทั้ง 3 ช่อง**
ซึ่งคือ **ค่าตั้งต้นที่โค้ดใส่ให้เมื่อแกะคำตอบของโมเดลไม่ได้** ไม่ใช่หน้าตาของโมเดลที่ตอบผิด
· ข้อที่ชัดมากอย่าง *"ประกาศจับเจ้าสัวดีกว่า🤣 ไอ้ตัวนำเข้าเงียบกันหมด"* ก็ได้ Neutral

### ต้นเหตุ

`max_tokens` ตั้งไว้ตายตัวที่ **2,600** · opus เขียนคำตอบยาวกว่า haiku/sonnet
→ **ถูกตัดกลางประโยค → JSON พัง → `extractJson` โยน error → โค้ดกลืน error แล้วเติม Neutral ให้ทุกข้อ**

### 🐞 บทเรียน — ความผิดพลาดอยู่ที่การออกแบบ ไม่ใช่แค่ตัวเลข

**"ไม่รู้" ถูกกลืนให้กลายเป็น "กลาง" แล้วรายงานออกมาเป็นคะแนน** ซึ่งดูเหมือนผลการวัดจริงทุกประการ
ถ้าไม่ได้สังเกตว่าตัวเลขมันผิดธรรมชาติ **เราจะสรุปว่า "opus ใช้ไม่ได้" ทั้งที่ไม่เคยได้คำตอบจาก opus เลยสักข้อ**
— เป็นกับดักเดียวกับที่ `CLAUDE.md` เขียนไว้ว่า *"ต้องไม่สรุปว่าไม่มีข้อมูล ทั้งที่ยังไม่รู้"*

### แก้แล้ว 3 ชั้น (worker v10 · หน้าเว็บ page-ver 5)

| ชั้น | เดิม | ตอนนี้ |
|---|---|---|
| เพดานโทเคน | ตายตัว 2,600 | คิดตามจำนวนข้อ `90 × n + 600` (สูงสุด 8,000) |
| คำตอบถูกตัดกลางคัน | ไม่รู้เลย | เช็ค `stop_reason === "max_tokens"` แล้ว **โยน error** |
| แกะ JSON ไม่ได้ | คืน Neutral ทั้งชุดเงียบๆ | **โยน error** — ก้อนนั้นถูกนับเป็น "ยิงพลาด" ไม่ใช่ผลการวัด |
| ข้อที่โมเดลไม่ได้ตอบ (`missing`) | หน้าเว็บนับเป็นคำตอบ Neutral | **ไม่นับ** + ถ้าเกิน 20% ขึ้นเตือนสีแดงว่าตัวเลขเชื่อไม่ได้ |

เทสต์ `tests/evalpage-missing.cjs` คุมไว้: จำลองว่าโมเดลไม่ตอบครึ่งหนึ่ง → ต้องวัดแค่ครึ่งที่ตอบจริง
และต้องขึ้นป้ายเตือน (ลองถอดการเช็ค `missing` ออก → ตก 2 ข้อทันที)

## 🔍 รอบ 7 — opus ยังพลาด แต่คราวนี้**บอกสาเหตุได้**

ตัวกันที่ใส่ไว้ทำงานถูกต้อง: 262 ข้อไม่ได้ผลกลับมา · ขึ้นเตือนว่าเชื่อไม่ได้ · **ไม่เดาแทน**
(ถ้าเป็นก่อนแก้ 262 ข้อนั้นจะกลายเป็น "กลาง" แล้วรายงานเป็นคะแนนหน้าตาดี)

ข้อความ error ที่ได้: `คำตอบถูกตัดกลางคัน (max_tokens 1140 / 2310 / 3930 / 4200)`

### 🎯 เบาะแสสำคัญ — ก้อนที่มีแค่ 6 ข้อก็ยังถูกตัด

| ก้อน | เพดานที่ให้ | JSON ที่ต้องการจริง |
|---|---|---|
| 6 ข้อ | 1,140 | **~150** |
| 40 ข้อ | 4,200 | ~1,000 |

ต้องการจริง 150 แต่ 1,140 ยังไม่พอ → **มีอย่างอื่นกินโทเคนก่อนถึง JSON**
= `opus` เขียนความคิด/คำนำก่อนตอบ ซึ่ง `haiku` กับ `sonnet` ไม่ทำ

> 📌 สูตรเดิมคิดเพดานจาก "จำนวนข้อ" อย่างเดียว จึงเผื่อส่วนนี้ไม่ได้เลย
> ยิ่งก้อนเล็กยิ่งเพดานต่ำ **ยิ่งพังง่ายกว่าก้อนใหญ่** ซึ่งขัดสามัญสำนึกและทำให้ไล่ผิดทาง

### แก้แล้ว (worker v11)

- เพดานใหม่ `60 × n + 4000` (สูงสุด 12,000) — มีส่วนเผื่อคงที่ก้อนใหญ่สำหรับคำนำ
- **ถูกตัด = ลองใหม่อัตโนมัติ 1 ครั้งด้วยเพดาน 2 เท่า** ก่อนจะยอมแพ้
  (ความยาวคำนำเดาไม่ได้ ต่างกันไปทุกก้อน — ลองใหม่ถูกกว่าตั้งเพดานสูงลิ่วทุกครั้ง)
- ยังถูกตัดอีก → โยน error พร้อมบอกว่าขยายเพดานแล้วยังไม่พอ **ไม่คืน Neutral เด็ดขาด**

เทสต์ `tests/retry.mjs` คุม 5 ข้อ: ลองใหม่แล้วได้ผลจริง · เพดานเป็น 2 เท่า · พลาดซ้ำต้องโยน error ·
ลองใหม่ครั้งเดียวไม่วนไม่จบ · เพดานตั้งต้นของก้อน 6 ข้อต้อง ≥ 4000 (กันไม่ให้ถอยกลับไปพังแบบเดิม)
